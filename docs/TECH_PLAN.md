# 러닝 시뮬레이터 기술 설계와 도구 선정안

작성일: 2026-10-02

확정한 화면은 왼쪽 트랙 주행과 오른쪽 자세 상세를 동시에 보여주는 웹 서비스다. 이 문서는 이를 구현할 언어와 도구의 권장안, 각 구성의 책임, 도입 순서와 검증 조건을 정한다. 화면 요구는 확정되었지만 기술 선정은 사용자 경험과 소규모 구현 검증을 반영할 권장안이다. 현재 설치·앱 구현·계정 생성·배포는 수행하지 않는다.

선정의 사용자 맥락은 시뮬레이션 개발 경험, 러닝에 대한 관심, 취미로 진행하는 개인 프로젝트, 웹·백엔드·클라우드 영역으로의 포트폴리오 확장이다. 구체적인 기존 언어와 엔진은 현재 프로젝트 문서에서 확인되지 않지만, 추가 자기소개를 기획 진행의 조건으로 두지 않는다.

사용자가 현재 Supabase와 Vercel을 사용하며 Vercel은 Pro 플랜이라고 확인했다. 배포와 데이터 저장은 이 환경을 우선 활용한다. Supabase의 요금제, 기존 프로젝트 구성과 남은 사용량은 미확인이다. 기존 서비스의 데이터베이스를 그대로 공유한다는 뜻은 아니며 이 프로젝트의 데이터 분리 방식은 연결 전에 정한다.

배포 방향 확인: 사용자는 웹은 Vercel, 후속 저장은 Supabase를 사용하고 무거운 서버 계산이 실제로 필요해지면 계산 부분에 AWS를 추가하는 제안에 동의했다. AWS 추가는 현재 도입 범위가 아니며 전체 웹 이전도 전제하지 않는다. 언어와 라이브러리 세부 조합은 권장안 상태를 유지한다.

## 권장 기술 조합

첫 화면은 TypeScript와 React로 만들고 Three.js를 React Three Fiber와 연결한다. 캐릭터와 동작은 Blender에서 준비한다. 검증된 신체 반응 계산을 도입할 때 Python과 FastAPI를 추가한다. 초기부터 모든 서버와 저장소를 운영하지 않고 필요한 단계에서 연결한다.

React Three Fiber는 Three.js를 React에서 사용하는 렌더러다. Drei의 View는 하나의 캔버스를 여러 화면으로 나누는 기능을 제공한다. 이 기능을 좌우 화면 구현에 활용하는 것이 본 프로젝트의 설계 제안이다. 라이브러리를 사용한다고 두 러너의 동작이 자동 동기화되는 것은 아니다. [React Three Fiber 설명](https://r3f.docs.pmnd.rs/tutorials/how-it-works), [Drei View 문서](https://drei.docs.pmnd.rs/portals/view)

Vite는 개발 서버와 배포 빌드를 제공하며 React·TypeScript 템플릿을 지원한다. 첫 버전의 단일 작업 화면에 사용한다. [Vite 문서](https://vite.dev/guide/)

## 좌우 화면의 실행 구조

브라우저 안에 실행 시간과 러너 상태를 관리하는 모듈을 하나 둔다. 화면을 그릴 때 이 공통 상태에서 경로 위치와 동작 시점을 얻어 두 화면에 적용한다.

1. 시작 시 체형, 경로 버전, 목표와 페이스를 이번 실행의 입력으로 고정한다.
2. 공통 시계가 일시정지와 배속을 반영한 시뮬레이션 시간을 만든다.
3. 이동 계산이 누적 거리와 트랙 위 위치, 진행 방향을 구한다.
4. 동작 제어가 같은 시간에 해당하는 달리기 자세를 구한다.
5. 왼쪽은 트랙 위치에 러너를 놓고, 오른쪽은 러너를 화면 중앙에 놓아 같은 자세를 크게 보여준다.
6. 화면의 거리·시간·바퀴 수는 같은 상태를 읽어 표시한다.

하나의 WebGL 렌더러에서 두 영역을 나눠 그리는 방식을 먼저 검증한다. 양쪽에 모델 인스턴스가 필요하면 관절 구조는 올바르게 복제하고 동일한 체형과 애니메이션 시간을 전달한다. 각 화면이 서로 다른 타이머로 동작을 진행시키지 않는다. 그리기 자체는 두 번 필요하므로 캔버스 하나가 비용을 절반으로 줄인다고 가정하지 않는다.

React는 버튼과 설정 등 UI를 관리한다. 매 프레임의 뼈와 좌표 갱신은 3D 루프에서 처리해 화면 전체를 매번 다시 구성하지 않도록 한다. 별도 상태 관리 라이브러리는 처음부터 추가하지 않고 실제 상태 공유 복잡도가 커질 때 검토한다.

첫 버전의 실시간은 브라우저에서 러너를 연속적으로 움직인다는 의미다. 서버 영상 스트리밍이나 매 프레임 네트워크 요청을 요구하지 않는다. 후속 서버 계산도 시간별 결과를 브라우저에서 재생하는 구조를 우선 검토한다.

## 캐릭터와 동작 제작

캐릭터 형태는 사용자의 명시적 선택에 따라 사람 형태의 전신 러너로 확정했다. 얼굴·복장·사실적 표현 수준과 사용할 에셋은 아직 정하지 않았다. 관절 구조가 있는 전신 모델을 기준으로 체형 변경과 동작을 검증한다.

캐릭터는 재배포와 수정이 허용된 모델을 확보하거나 직접 만든다. 모델 및 달리기 동작 각각의 출처와 이용 조건을 기록한다. 특정 모델 판매처나 유료 에셋 구매는 아직 선택하지 않는다.

Blender 원본에는 관절 구조와 체형 변형 규칙을 보관하고 웹에는 GLB를 제공한다. Blender의 glTF 내보내기에서 지원되는 기능 안으로 애니메이션을 정리한다. 편집기의 제약 조건이나 효과가 그대로 웹에 옮겨진다고 가정하지 않고 필요하면 동작을 키프레임으로 변환해 검증한다. [Blender glTF 문서](https://docs.blender.org/manual/id/5.0/addons/import_export/scene_gltf2.html)

초기 달리기 동작은 제자리에서 반복하는 하나의 동작을 기준으로 제안한다. 트랙 이동은 별도 경로 계산이 담당한다. 체형 변경은 단순히 몸 전체를 가로세로 늘리는 방식으로 처리하지 않는다. 관절 길이 변경과 외형 변형을 조합할 수 있는 모델을 선정하고, 극단적인 값에서의 관통·발 미끄러짐을 확인한다.

오른쪽 자세 표시의 점과 선은 모델의 관절에서 얻는다. 웹캠, 영상 자세 추정과 AI 학습은 현재 요구에 없다. 관절이 표시된다는 이유로 실제 신체의 관절 토크나 피로를 알 수 있는 것은 아니다.

최우선 검증은 [설정값에 따른 전신 캐릭터 조절](CHARACTER_VALIDATION.md)이다. 정지한 캐릭터에서 입력 치수, 변형 후 측정 치수와 관절 위치를 확인한다. 이 검증을 통과하기 전에는 달리기와 좌우 동기화를 첫 성공 기준으로 삼지 않는다.

체형 조절 검증을 통과한 뒤 동작 연결 단계의 통과 조건은 다음과 같다.

- 같은 캐릭터를 양쪽에서 표시하고 같은 순간에 멈출 수 있다.
- 측면·정면·후면 전환과 관절 표시가 동작한다.
- 대표 체형 몇 가지에서 팔다리와 발이 눈에 띄게 깨지지 않는다.
- 속도와 동작 반복 주기의 관계를 설명할 수 있다. 반복 주기 변경은 아직 기획 결정이 필요하다.
- 확보한 모델과 동작을 웹 서비스에 배포할 수 있는 조건을 확인했다.

이 검증이 실패하면 캐릭터 에셋, 지원 치수 범위 또는 동작 방식을 재설계한 뒤 전체 UI 구현으로 진행한다.

## 실제 트랙 자료 처리

QGIS는 확보한 경로 자료를 검토하는 도구로 선택한다. QGIS 자체가 롯데가든파크 트랙의 정확한 데이터를 제공한다고 가정하지 않는다. GPS 자료가 있다면 GPX 등을 읽어 확인할 수 있다. [QGIS GPS 자료 안내](https://docs.qgis.org/3.44/en/docs/user_manual/working_with_gps/plugins_gps.html)

자료 흐름은 출처 확인 → 주행 선 선정 → 거리 기준 확인 → 미터 좌표 변환 → 웹용 파일 생성 → 화면과 거리 검증이다. 위도·경도 숫자를 그대로 미터 좌표처럼 사용하지 않는다. 원본 좌표계와 변환 방법을 기록하고, 곡선 보정으로 바뀐 길이를 확인한다.

첫 버전은 가공한 코스 파일을 함께 배포하므로 지도 API를 주행 내내 호출할 필요가 없는 구조를 제안한다. 다만 원자료의 이용 조건이 이러한 가공과 배포를 허용해야 한다. 고도와 트랙 폭이 없으면 임의의 측량값으로 채우지 않는다.

## 계산 서버와 결과 저장

계산 연구는 Python에서 시작한다. 논문과 자료로 기준 계산을 재현한 뒤 독립적인 평가 기준과 적용 범위를 기록한다. 검증된 계산을 웹에 연결할 때 FastAPI로 입력과 결과 구조를 정의한다. FastAPI는 OpenAPI 기반 API 명세를 제공한다. [FastAPI 기능](https://fastapi.tiangolo.com/features/)

입력에는 체형과 단위, 경로 버전, 주행 조건, 모델 버전을 포함한다. 출력에는 계산 상태, 시간별 관측량, 요약 결과와 적용 범위를 포함한다. 웹과 Python은 서로 다른 단위나 기본값을 사용하지 않도록 공통 예제 입력·출력을 검증한다.

오래 걸리는 계산이 확인될 때 실행 작업과 별도 계산 프로세스를 도입한다. 초기부터 메시지 큐, WebSocket과 여러 서비스를 추가하지 않는다. UI를 막는 계산을 API 요청 처리 중 계속 실행하는 방식도 성능 측정 없이 채택하지 않는다.

영구 기록이 필요해지면 기존 사용 환경인 Supabase의 PostgreSQL에 실행 입력과 요약, 버전을 저장한다. 별도로 관리할 모델 파일과 대량 시간별 결과는 Supabase Storage를 우선 검토한다. 첫 버전의 고정 코스와 작은 모델은 웹 배포 파일에 포함할 수 있다. 같은 파일을 양쪽에 불필요하게 중복 저장하지 않는다. Supabase는 프로젝트마다 PostgreSQL 데이터베이스와 파일 저장 기능을 제공한다. [Supabase DB](https://supabase.com/docs/guides/database/overview), [Supabase Storage](https://supabase.com/docs/guides/storage)

Supabase를 사용하고 있다는 이유로 첫 버전에 로그인·기록 저장을 추가하지 않는다. 첫 주행 버전은 기존 기획대로 세션 기록만 유지할 수 있다. 개인 기록 저장을 도입할 때 Supabase Auth와 사용자별 접근 규칙을 함께 설계하고, 브라우저에 관리자용 비밀 키를 넣지 않는다. 기존 프로젝트 공유 또는 신규 프로젝트 생성은 데이터 분리와 비용을 확인한 뒤 결정한다. [Supabase 접근 제어](https://supabase.com/docs/guides/database/postgres/row-level-security)

## 배포와 운영

첫 구현은 로컬에서 실행하고 공개 웹은 사용자가 이미 이용하는 Vercel Pro에 배포하는 방향으로 정리한다. Vercel은 Vite 앱 배포를 지원하므로 현재 TypeScript·React·Vite 권장안을 유지할 수 있다. 실제 3D 주행은 방문자의 브라우저에서 실행하며 Vercel에서 매 프레임 영상을 생성하지 않는다. [Vite on Vercel](https://vercel.com/docs/frameworks/frontend/vite)

Python 계산 API가 필요해지면 Vercel의 FastAPI 지원을 먼저 검토한다. 실행 시간·메모리·패키지 크기 한도 안에 들어가는지는 실제 계산으로 측정한다. 오래 걸리는 계산이나 별도 실행 환경이 필요한 경우에만 외부 계산 서버를 검토한다. 이 선택은 아직 서버 배포 확정이 아니다. [Vercel FastAPI](https://vercel.com/docs/frameworks/backend/fastapi), [Functions 한도](https://vercel.com/docs/functions/limitations)

AWS와 Cloudflare는 현재 배포 계획에서 제외한다. 기존 Vercel·Supabase로 요구를 충족하지 못하는 근거가 생길 때 재검토한다. 현재 단계에서는 계정이나 외부 프로젝트를 만들거나 수정하지 않는다.

배포 전에는 파일 용량과 전송량, 서버 실행 시간, 저장 용량을 기준으로 월 비용을 산정한다. 무료 운영을 보장하지 않는다. 기본 예산 경보와 배포 되돌리기 절차를 정하고, 자동 검사를 통과한 버전만 배포하는 흐름을 준비한다.

## 개발과 검증 도구

Git으로 코드와 기획 변경을 관리한다. 원격 저장소를 정하면 GitHub와 자동 검사 도구를 연결하는 안을 제안한다. 모델 원본처럼 큰 파일은 크기와 배포 방식이 정해진 뒤 별도 저장 또는 Git LFS 사용 여부를 결정한다. Figma는 화면 세부 설계가 필요해질 때 추가할 수 있지만 현재 시안과 화면정의서 진행의 필수 조건은 아니다.

웹의 거리·시간·바퀴 계산은 Vitest로 검증하고, 시작·정지·배속·완료 등 사용자 흐름은 Playwright로 검증한다. 3D 외형과 발 접촉은 실제 화면으로 확인하며 스크린샷 하나로 수치 계산 정확성을 판단하지 않는다. [Vitest 안내](https://vitest.dev/guide/), [Playwright 안내](https://playwright.dev/docs/intro)

성능 목표의 초안은 기준 PC와 브라우저를 정한 뒤 1440 × 900 화면의 두 뷰에서 60fps를 목표로 하고, 지속적인 30fps 미만 구간을 개선 대상으로 삼는 것이다. 이것은 측정한 성능이 아니다. 기준 PC의 CPU·GPU·메모리, 브라우저 버전, 모델 복잡도와 해상도 배율을 함께 기록한다. 공개 버전의 다운로드 크기와 첫 로딩 시간 한도는 모델 후보를 확보한 뒤 설정한다.

라이브러리는 구현 착수 시 서로 호환되는 안정 버전을 확인해 잠금 파일에 기록한다. Node.js는 선택한 Vite가 지원하는 LTS 계열을, Python은 계산 라이브러리가 지원하는 버전을 사용한다. 조사하지 않은 정확한 버전을 지금 임의로 확정하지 않는다.
